# v1.6.2 — Workspace information architecture

v1.6.2 began as a focused desktop workspace usability specification and is now
implemented as the corresponding presentation and navigation pass. It changes
no API contracts, stored schemas, explicit-save semantics, revision checks, or
browser-local draft preservation.

## Implemented

- Paper Detail displays extracted abstracts in a readable 72-character content
  column. Display-only wrapped lines are joined while blank-line paragraphs
  remain separate; stored abstract metadata is never changed.
- Projects opens on the project overview and linked Papers/Note Blocks.
  Project creation and link add forms are now explicit disclosures; linked
  research material uses readable cards while existing remove, orphan, archive,
  revision, and draft-safety behavior remains available.
- Settings is a restrained workspace landing page. The existing application,
  workspace, integrity, and backup-health information is retained in the new
  `/settings/diagnostics` view.
- Tags leads with candidate review and canonical registry browsing. Tag create
  and selected-tag management are disclosed, category labels are readable,
  canonical keys are advanced details, and aliases use compact removable chips.
- Library keeps its selected-paper inspector, adds persistent filter labels,
  visible filter state and reset, compact tag chips, and clearer diagnostics
  actions for attention states. Selection works from a keyboard, dismissal
  returns focus to the selected row, and a direct Paper Detail link remains
  visible beside selection.

## Implementation evidence and supported limits

- The pure `abstractDisplayParagraphs` display adapter joins extracted
  soft-wrapped lines and preserves blank-line paragraph boundaries. Whitespace-
  only abstracts use the same empty state as an absent abstract.
- Projects and Tags restore focus to their Create action when the disclosed
  form closes. The Library inspector restores focus to the row used to open it.
- The Tags candidate summary remains aggregate because the existing
  `GET /tags/summary` read model does not identify the Papers containing those
  candidates. Its action now opens Library with clear guidance to select a
  Paper and use its existing Reader tag-review workflow; no aggregate candidate
  endpoint or background scan was added.
- A `PaperDetail.project_links` entry contains a project ID, link type, and
  target type, but not a safe project display name. Library therefore shows the
  available linked-project count and does not expose raw IDs or invent names.

## Validation scope

Focused frontend coverage verifies abstract display normalization, collection
and management disclosures, Settings-to-Diagnostics routing, tag registry
presentation, candidate-review handoff, focus restoration, and Library
selection/filter affordances. Automated validation is recorded in the
generated [Current Release Status](../CURRENT_RELEASE_STATUS.md). Desktop and
narrow-width browser checks remain manual evidence and are not claimed here.
