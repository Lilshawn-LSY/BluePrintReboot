# v1.5.3 Settings and Health Safe Read Parity

Status: implementation complete; local automated validation recorded in the canonical release manifest; manual runtime and hosted/publication evidence remain separate.

## Summary

v1.5.3 removes the final frontend Settings placeholder and adds one strict, read-only Settings summary. The web page now shows Application, Workspace, Data integrity, and Backup readiness using real supported local facts or explicit unavailable states.

This completes roadmap items R-112 and R-113 and the implementation portion of G2 Frontend Read Parity. It does not add any Settings write, configuration editor, backup/restore command, repair action, Project/Tag write, or Note-link expansion.

## API contract

`GET /settings/summary` returns:

- `application`: healthy API state, canonical product version, and matching API contract version.
- `workspace`: fixed resources for papers, notes, Projects, canonical Tags, note blocks, and Project links; each has `healthy`, `warning`, `empty`, or `unavailable` state and a numeric count or null.
- `data_integrity`: fixed `missing_pdfs`, `unindexed_pdfs`, `orphan_notes`, `orphan_note_blocks`, `orphan_project_links`, and `corrupt_json` checks; each has state, count or null, severity, safe explanation, and safe next action.
- `backup_readiness`: safe snapshot-evidence presence plus a UTC last-updated time only when evidence exists.

The contract deliberately excludes executable/package/process information, host or environment values, paths, filenames, hashes, manifests, restore targets, raw configuration, arbitrary dictionaries, exceptions, and private records.

## Performance and mutation boundary

The Settings reader is separate from the full Library Health Check. It caps discovered filesystem entries, paper-index bytes and rows, per-file JSON reads, and total JSON bytes per request. It checks app-owned metadata and file presence only.

Settings load does not:

- hash or parse PDFs;
- extract text;
- open or verify backup archives;
- verify a restore target;
- create a backup;
- migrate, normalize, repair, clean, or rebuild data;
- write a cache, report, status, release-state, or user-data file.

Partial component failures remain successful section/item-level unavailable states. A complete construction or strict-adaptation failure uses the existing generic 503 response.

## Frontend

`/settings` now consumes the typed safe summary through the existing same-origin bridge and shared resource hook. It renders verified empty and zero states distinctly from unavailable diagnostics, keeps partial warnings local to the affected section/item, and provides the established retry behavior for API-offline or controlled read-model failures.

The page contains no controls for configuration, workspace/API address changes, backup, restore, repair, data removal, logs, debug exports, or other deferred actions. Static guidance points to the existing Streamlit Settings workflow.

## Known limitations and deferred scope

- Lightweight integrity counts are intentionally narrower than the explicit Streamlit Library Health Check.
- A capped or unreadable diagnostic is reported as unavailable rather than guessed as zero.
- Snapshot evidence means a matching snapshot file is present; Settings does not open or verify the archive.
- Settings writes, backup creation, restore, repair, configuration editing, debug export, Project/Tag writes, Note-link expansion, and broader UI redesign remain deferred.
- No pull request, hosted CI, merge, tag, GitHub Release, or post-merge `main` evidence is claimed by this draft.
