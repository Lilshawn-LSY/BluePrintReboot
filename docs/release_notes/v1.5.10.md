## Canonical Tag Book governance

The existing Tag Book remains the only canonical registry. Its explicit commands create a canonical tag, update bounded user-managed metadata (label, category, description, and suggestion strength), add or remove an alias, and deprecate a tag. Canonical keys remain stable identities; ordinary destructive deletion and key renaming are absent.

Every governance write carries the registry revision, acquires the shared workspace lock, reloads inside the lock, uses the existing atomic Tag Book persistence, and returns a controlled conflict if the revision is stale. A category remains bounded Tag Book metadata, not a hierarchy or ontology editor.

Alias identity follows the repository's existing conservative normalization. The service rejects duplicate aliases, aliases that collide with a canonical identity, canonical labels that collide with an existing alias, ambiguity, and self-aliasing. It does not introduce broader scientific-term normalization.

Deprecation retains the canonical record, aliases, historical Paper relationships, and inspectability. It prevents new ordinary candidate approval, promotion, or application; it does not remove a tag from any Paper. Existing legacy or noncanonical Paper tag text is likewise neither deleted, renamed, nor rewritten by governance actions.

## Candidate review and explicit application

Candidate generation reuses the current Tag Book/extracted-text rulebook path. It writes only a small persisted per-Paper review context, including the generated tag text, canonical resolution when present, source/evidence, supplied score/confidence, and review state. Generation never changes the Paper index or the Paper's applied tag list.

The Reader makes review actions explicit:

1. Generate or view candidates.
2. Approve a candidate with an active canonical resolution, or reject it.
3. Promote an unresolved candidate to a new or already-resolved active canonical Tag Book entry; promotion preserves the candidate review record and avoids duplicate canonical/alias identities.
4. Choose the separate Apply action to invoke the existing v1.5.7 `ReaderCommandService.add_paper_tag` path.

The Apply command carries both the candidate-review revision and the existing Paper tag revision. It preserves v1.5.7 locking, atomic index persistence, revision conflict handling, no-op behavior, and Reading Note-header compatibility. Candidate review operations do not replace an unsaved Reader note draft. Rejected candidates remain rejected in the persisted context until the user deliberately resets/re-generates that context.

## Candidate-quality baseline

`tests/fixtures/tag_candidate_quality_corpus.json` is a deterministic three-case baseline over the existing rulebook. The current measured result is: 2 expected candidates, 2 expected candidates present, 0 misses, 1 false-positive candidate, and precision-like `0.667`. This is a regression signal for the present rules, not a claim of model or scientific-tagging quality.

Deferred: automatic application, automatic cleanup or bulk retagging, embeddings/vector tagging, new LLM providers, ontology/tree editing, graph inference or visualization, citation/Zotero workflow, ingestion/enrichment changes, backup/recovery redesign, and the Reader visual overhaul. v1.8.0 owns future tag-intelligence work.
